# SafeBand Guardian: Security & Privacy Architecture

## 1. Threat Model & Security Objectives

SafeBand Guardian is designed to protect vulnerable children while eliminating traditional surveillance risks associated with commercial trackers.

### Core Security Objectives:
1. **Prevent Unauthorized Access to Parental Controls:** Children, unauthorized peers, or malicious actors must not be able to disable safety monitoring, alter safe zones, or bypass device lockdown.
2. **Prevent Community Surveillance & Eavesdropping:** Third-party smartphones participating in community emergency relay must never gain access to child identity, medical history, or parent contact details during normal operations.
3. **Prevent Malicious Injection & Forgery:** Hardware telemetry, pairing challenges, and application updates must be cryptographically validated before acceptance.
4. **Prevent Credential Exfiltration:** Sensitive credentials (master PINs, session tokens, audit hashes) must never be extracted via unencrypted Android system backups.

## 2. Role-Based Access Control (RBAC) & Boundary Isolation

### 2.1 Dual-Role Architecture in Single Binary
The application enforces strict separation between `AppRole.PARENT` and `AppRole.CHILD`.

```
                    ┌───────────────────────────────┐
                    │      AccessController         │
                    └───────────────┬───────────────┘
                                    │
               ┌────────────────────┴────────────────────┐
               ▼                                         ▼
      Parent Role Operations                    Child Role Operations
      - Configure Safe Zones                    - Display Reassurance Pill
      - Create Journey Corridors                - 2-Second Hold Tactile SOS
      - Generate 15-min Pairing PINs            - Emergency Helpline Dialing
      - Provision New Wearables                 - Local Sensor Fall Detection
      - View Full Audit Log                     - Receive Ambient Heartbeats
      - Alter Master PIN                        (BLOCKED from parent APIs)
```

### 2.2 ViewModel & Repository Layer Enforcement
Security is NOT enforced solely by hiding UI buttons. Methods that modify system state enforce role checks programmatically:
```kotlin
// Example: SafeBandViewModel.kt
fun updateSafeZone(zone: SafeZoneEntity) {
    accessController.requireParentRole() // Throws SecurityException if called from Child role
    viewModelScope.launch {
        safetyRepository.saveSafeZone(zone)
    }
}
```
Any attempt to call privileged APIs from Child mode triggers an immediate `SecurityException`, logged to the tamper-evident blackbox.

## 3. Child Lockdown Security

### 3.1 PIN Verification Semantics
- **Rejection of Arbitrary Codes:** The child interface cannot be unlocked using arbitrary 6-digit numbers. Only the configured master PIN (stored securely in DataStore) or an active single-use provisioning challenge is accepted.
- **Rate-Limiting & Exponential Cooldown:** Entering an incorrect PIN records a failed attempt. After 5 consecutive failed attempts, the entry keypad is locked for 60 seconds. Additional failures double the cooldown interval.
- **Tamper Alert on Excessive Failures:** Exceeding 10 failed unlock attempts triggers an internal `MEDIUM` risk anomaly, dispatching an alert notification to the primary guardian.

### 3.2 Single-Use Provisioning Challenges
- Pairing challenges generated by parents are 6-digit numbers generated via `java.security.SecureRandom`.
- Each challenge has a strict **15-minute Time-To-Live (TTL)**.
- Once successfully claimed by a child device, the challenge state immediately transitions to `CLAIMED` and cannot be re-used to authorize another session.

## 4. Authentication Architecture

### 4.1 Google Sign-In via Android Credential Manager
- Implemented using modern `androidx.credentials.CredentialManager` and `com.google.android.libraries.identity.googleid`.
- Secure JWT payload parsing: Decodes the base64 ID token to extract the exact Google Subject Identifier (`sub`), verified email (`email`), full display name (`name`), and avatar picture URL (`picture`).
- Nonce verification: Generates a cryptographically random SHA-256 hashed nonce on each sign-in request to prevent token replay attacks.
- Robust exception handling: Explicitly catches `NoCredentialException`, `GetCredentialCancellationException`, and `GetCredentialException`, ensuring the app never crashes when Google Play Services is absent or accounts are not registered.

### 4.2 Offline Guest Parent Mode
To maintain reliability in disaster zones, remote areas, or un-Googled devices:
- Parents can choose **"Offline Guest Parent"** during first launch.
- Generates a local, deterministic pseudonymous identifier (`PARENT-GUEST-...`).
- Grants full local control over geofences, BLE monitoring, and band pairing without external network communication.

## 5. Privacy-Preserving Relay System

### 5.1 Multi-Packet Interleaved Broadcasting
To prevent bystander tracking:
1. **Normal State:** Wearables transmit no personal data.
2. **Emergency State:** The device cycles through 3 distinct packet types every 1200ms:
   - `0x01 (Core Telemetry)`: Device ID, Risk Level, Timestamp, GPS Coordinates.
   - `0x02 (Bio Core)`: Child First Name (12 bytes), Age (1 byte), Blood Group (3 bytes).
   - `0x03 (Contact Phone)`: Primary Guardian Phone Number (16 bytes).

### 5.2 Zero Leakage to Relaying Smartphones
When a bystander phone running SafeBand Guardian detects an emergency broadcast:
- The bystander phone acts as an opaque transport node.
- The emergency payload is forwarded to the backend or emergency hub without displaying or persisting the child's identity, age, or medical details on the relaying device.
- Bystander phones retain no records of nearby child wearables in their local databases.

## 6. Data Protection & Backup Rules

### 6.1 Unencrypted Backup Exclusions
Sensitive configuration and security state are explicitly excluded from Android ADB backups and cloud auto-backups in `res/xml/backup_rules.xml` and `res/xml/data_extraction_rules.xml`:
- Excluded: `safeband_preferences.preferences_pb` (DataStore master PIN, session tokens).
- Excluded: `safeband_database` and WAL files (Room database containing child records and audit logs).
- Included: Non-sensitive general UI theme settings only.

### 6.2 Immutable SHA-256 Audit Blackbox
All incident triggers, status changes, and unlock attempts are logged to an append-only audit table. Each entry contains:
- Unix timestamp
- Action description
- AppRole of the triggering actor
- SHA-256 hash chaining the previous record's hash to ensure tamper evidence.
